# План развития im-human — Milestone v2.2 (2026-07-11)

> Следующий milestone после v2.1. В v2.1 остаётся стабилизация: воспроизводимость,
> Save/Load в UI, честная маркировка `biologicalAge`, справка, базовая безопасность
> зависимостей и измеримая производительность дашборда.
>
> v2.2 — это уже не «починить доверие», а аккуратно расширить продукт: экспорт результатов,
> новые механики модели и первые формальные связи с остальной линейкой.
>
> Разработка ведётся через GSD. Так как текущий `.planning/ROADMAP.md` ведёт v2.0 до Phase 13,
> а [Milestone v2.1. Development Plan_2026-07-10](Milestone%20v2.1.%20Development%20Plan_2026-07-10.md) занимает Phase 14–16,
> v2.2 разложен на следующие реальные фазы **Phase 17–21**.

---

## 1. Условия входа в v2.2

Начинать v2.2 только после того, как v2.1 закрыт по проверяемым критериям:

- Save/Load доступен из UI, ручной round-trip сохранения и загрузки пройден.
- `biologicalAge` в интерфейсе помечен как ориентировочный индекс, не медицинская метрика.
- UI-дисклеймер и пункт «Справка» доступны из приложения.
- Зависимости зафиксированы верхними границами или lock-файлом; `pip-audit` выполнен хотя бы один раз.
- UI-производительность проверена: обновляются только видимые графики, PyOpenGL включён только если замер до/после показывает пользу.
- Вики и Neo4j синхронизированы после документационных изменений.

---

## 2. Цель v2.2

Сделать im-human полезнее как исследовательский инструмент, не меняя архитектурные границы:
`domain` описывает данные, `engine` считает модель, `ui` показывает сценарий, Obsidian остаётся
ground truth, Neo4j — поисковый и графовый слой.

**Главный принцип:** одна новая механика за раз, с формулой в `06 - Engine/`, тестами и явной
пометкой уровня уверенности.

---

## 3. GSD-фазы Milestone v2.2

### Phase 17 — Results Export (Экспорт результатов)

- **[ ] Экспорт графиков в PNG/SVG** из дашборда биомаркеров.
- **[ ] Экспорт краткого отчёта сценария**: профиль, вещества, период, ключевые изменения биомаркеров, предупреждения.
- **[ ] Документация в [User Guide](../06%20-%20Engine/User%20Guide.md)**: где сохраняются файлы и что означают экспортируемые числа.

**Критерий готовности:** пользователь может сохранить визуальный результат симуляции без скриншотов
и открыть файл вне приложения.

### Phase 18 — Biological Age Calibration (Калибровка age-index)

- **[ ] Пересмотреть `mortality_risk.py`** только при наличии более полных эталонных данных PhenoAge.
- **[ ] Если данных нет** — оставить текущую модель как ориентировочный индекс и не менять формулу.
- **[ ] Добавить страницу калибровки** в `06 - Engine/` или обновить [Biological Age Formula](../06%20-%20Engine/Biological%20Age%20Formula.md) с разделом
  «что откалибровано, что является допущением».

**Критерий готовности:** решение зафиксировано: либо новая формула имеет источник, тесты и понятное
ограничение применимости, либо текущая формула явно оставлена как ориентировочный индекс.

### Phase 19 — Model Mechanics v2 (Одна новая механика модели + расписание приёма)

**Расписание приёма (DOS-01) — предпосылка для точных PK/PD и будущих циркадных ритмов:**
- **[ ] Несколько фиксированных времён приёма в сутки для одного вещества** (например, 10:00 и
  14:00 — режим «2 раза в день»), а не одно `hour_of_day` на расписание. Сейчас
  `IntakeSchedule.hour_of_day` (`src/domain/substance.py`) — одно значение 0–23;
  `IntakeSchedule.interval_hours` объявлено (D-07) и покрыто тестами, но движком не используется
  (`AdaptiveStepper.should_dose` проверяет только `hour_of_day`/`start_tick`/`duration_ticks`/`cycle`);
  UI (`src/ui/substance_manager.py`) даёт один `QSpinBox` часа и блокирует повторное добавление
  того же вещества (WR-03) — реалистичный режим «2 раза в день» сейчас недоступен без обхода UI.
- **Направление решения (design-level, детализируется в discuss-phase перед планированием):**
  расширить `IntakeSchedule` до списка времён приёма **или** разрешить несколько расписаний на
  один `substance_id` с разным временем; обновить `should_dose()` под проверку членства в списке;
  обновить диалог добавления вещества под несколько времён; решить судьбу мёртвого поля
  `interval_hours` (задействовать или удалить).
- **Критерий готовности:** пользователь задаёт ≥ 2 времени приёма для одного вещества через UI;
  тест на детерминизм (дозы прикладываются ровно на заданных часах, не «размазаны» по тикам);
  документация схемы расписания обновлена в [User Guide](../06%20-%20Engine/User%20Guide.md).

**Одна новая биологическая механика (реализовывать по одной, не пачкой):**

| Механика | Польза | Условие старта |
|---|---|---|
| Субсуточные тики | Точнее моделировать PK/PD коротких эффектов | Есть benchmark, что UI/engine выдерживают более частые шаги |
| Циркадные ритмы | Реалистичнее глюкоза, пульс, HRV, кортизол-подобные паттерны | Есть минимальная формула и тесты суточной периодичности |
| Генетический профиль | Персонализация APOE/CYP3A4/VDR и т.п. | Есть ясная схема данных и безопасные значения по умолчанию |
| Нелинейная PD (EC50/Hill/IC50) | Уйти от грубых линейных эффектов веществ | Есть один пилотный biomarker/substance pair с источником |
| A/B-сравнение сценариев | Сравнивать интервенции, а не только смотреть один прогон | Save/Load и экспорт результатов уже стабильны |

**Критерий готовности:** каждая механика (включая расписание приёма) добавляет тесты, документацию
формулы/схемы и не дублирует физику в нескольких местах.

### Phase 20 — Mortality Evidence Integration (Связь с mortality KB)

- **[ ] Формализовать ссылку mortality → human** для уровней доказательности веществ.
- **[ ] Не дублировать научные досье** из mortality: в human хранить только параметры симуляции и ссылку вида `[[mortality:концепт]]`.
- **[ ] Сделать пробный query-путь**: вещество в human → evidence summary из mortality → отображение/tooltip в UI.
- **[ ] Добавить модель `EffectEvidence`** для связи `substance → biomarker`: направление эффекта, сила/коэффициент,
  confidence, источник/ссылка на mortality KB, версия параметра и статус применения в симуляции.
- **[ ] Спроектировать data registry для no-code расширения**: схемы и валидатор для веществ, биомаркеров,
  reference ranges, max-safe limits, interactions и formula/effect metadata. В v2.2 это дизайн и один пилот,
  а не массовая миграция каталога.
- **[ ] Зафиксировать Core 50–70 как следующий горизонт**, составить shortlist категорий и критерии включения:
  частота доступности в реальных анализах, влияние на модель, наличие evidence/provenance, понятная единица измерения,
  безопасный диапазон и UI-смысл.

**Критерий готовности:** хотя бы одно вещество показывает evidence-level, полученный из внешнего knowledge layer,
без копирования большого текста в human; есть черновая схема `EffectEvidence`/data registry и список Core 50–70
помечен как кандидат следующего milestone, а не как обязательство v2.2.

### Phase 21 — Human-Agent Data Integration Contract (Связь с agent)

- **[ ] Рассмотреть Hovorka-модель из `agent`** как источник данных/результатов для Глюкоза/Инсулин/HOMA-IR.
- **[ ] Не переносить код автоматически**: сначала определить контракт данных и проверить, что `agent`
  закрыл свои стабилизационные блокеры.
- **[ ] Базовый вариант реализации — data-level integration**: Agent производит результаты, Human потребляет
  их как внешний слой физиологических данных.
- **[ ] Message broker — как транспортный вариант после контракта**, если нужны очереди долгих расчётов,
  ретраи, статусы и асинхронная обработка сценариев.
- **[ ] Engine-level adapter — крайний вариант**: Human вызывает внешний движок Agent через стабильную границу
  (CLI/API/library boundary), но Agent остаётся владельцем Hovorka-логики.

**Предпочтительная архитектура:**

1. **Data contract first** — зафиксировать форматы `SimulationTrace`, `InterventionProtocol`,
   `ModelProvenance`, `ValidationReport`, `BiomarkerMapping`.
2. **Transport second** — сначала файл/таблица для воспроизводимости; broker только если появится реальная
   потребность в асинхронных job-очередях.
3. **Engine adapter last** — только если data-level интеграции недостаточно для интерактивного сценария.

**Вариант с брокером сообщений:**

- Human публикует событие/команду `glucose_insulin.simulation.request`.
- Agent забирает задачу, считает сценарий и публикует `glucose_insulin.simulation.completed` или
  `glucose_insulin.simulation.failed`.
- Human сохраняет результат как внешний trace, мапит его в biomarker-сигналы и показывает provenance.
- Контракт сообщений должен быть версионирован; обязательны `scenario_id`, `schema_version`,
  `model_version`, `created_at`, `status`, `errors`, `trace_uri` или inline trace summary.
- Брокер не должен становиться обязательной зависимостью локального single-user запуска до подтверждённой
  потребности.

**Критерий готовности:** есть отдельный design note с контрактом данных, сравнением transport-вариантов
(file/table, API/CLI adapter, message broker) и решением «data-only / broker-backed / engine-adapter / отложить».

## 4. Что не входит в v2.2

- Мульти-юзер, облако, микросервисы, веб-версия, Telegram-бот.
- Общий монорепозиторий для mortality · human · agent.
- Полная унификация `.neo4j/` в библиотеку без измеренной боли поддержки.
- Медицинские рекомендации, diagnosis-like wording или усиление claims без юридической и научной проверки.
- Массовое расширение каталога до Core 50–70 биомаркеров. В v2.2 закладывается только evidence/data-registry
  фундамент и shortlist; само расширение должно идти отдельным milestone после валидатора.

## 4.1. Кандидат следующего milestone после v2.2

**Milestone v2.3 — Core Biomarker & Substance Registry Expansion**:

- **Phase 22 — Data Registry Implementation:** единый реестр биомаркеров/веществ, JSON Schema или Pydantic-валидация,
  проверка ссылок `effectProfile → biomarker`, единиц, диапазонов и max-safe limits без правки Python-кода.
- **Phase 23 — Core 50–70 Biomarkers:** расширение MVP-24 до клинического Core 50–70, только для маркеров
  с понятным source/provenance, reference ranges и UI-группировкой.
- **Phase 24 — No-code Substance Authoring:** форма или wizard для добавления вещества с PK, эффектами,
  взаимодействиями и ссылками на mortality KB; экспорт/импорт как data pack.

## 5. Порядок работ

1. **Phase 17:** экспорт графиков PNG/SVG и короткого отчёта сценария.
2. **Phase 18:** решение по biologicalAge: либо калибровка при наличии данных, либо явная фиксация «оставляем как индекс».
3. **Phase 19:** сначала расписание приёма (DOS-01, меньше по объёму и не биологическая механика — разблокирует реалистичное многократное дозирование), затем одна новая биологическая механика модели, предпочтительно A/B-сравнение или нелинейная PD на одном пилотном кейсе.
4. **Phase 20:** пробная интеграция evidence-level из mortality + схема `EffectEvidence`/data registry + shortlist Core 50–70.
5. **Phase 21:** design note по Human-Agent data contract и возможным transport-вариантам, включая брокер сообщений.
