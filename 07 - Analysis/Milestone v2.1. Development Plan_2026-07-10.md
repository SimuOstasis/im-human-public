# План развития im-human — Milestone v2.1 (2026-07-10)

> Форвардный план развития **именно приложения im-human**. Синтезирует три источника:
> собственный технический review ([Application Development Review_2026-06-28](Application%20Development%20Review_2026-06-28.md)),
> ревью родственного проекта `agent` (BioAgent Control Lab, 2026-07-02) — как источник
> переносимых инженерных уроков, и сквозной `Product Line Development Plan` — как рамку
> фаз 0–4 (в сквозном плане линейки они названы «волнами»), где инфраструктура делается один раз на линейку.
>
> Отдельным блоком включены **шаги 1–2 улучшения производительности UI** (пункты 3–7
> того же анализа планируется к моменту выхода на этот блок уже выполнить).

## 0. Комментарий после проверки плана (2026-07-11)

План в целом согласуется с линейкой mortality · human · agent: правильное направление — **A → B**
(стабилизация, затем постепенное развитие), без облака, мульти-юзера, микросервисов и переписывания.
Главная правка по версии: исходный документ смешивал три разных горизонта — стабилизацию v2.1,
собственные v2-фичи и межпродуктовую интеграцию. Для Milestone v2.1 это слишком широко.

**Граница v2.1:** релиз доверия и удобства, оформленный как реальные GSD-фазы **Phase 14–16**.
В нём должны остаться только работы, которые повышают воспроизводимость, честность UX,
доступность уже готового backend и измеримую отзывчивость UI.

**Вынесено в v2.2:** экспорт графиков, пересмотр калибровки `mortality_risk.py`, новые механики
модели (субсуточные тики, циркадные ритмы, генетический профиль, EC50/Hill/IC50, A/B-сценарии),
формализация связи mortality → human и потенциальный перенос Hovorka-модуля из `agent`.
Новый план: [Milestone v2.2. Development Plan_2026-07-11](Milestone%20v2.2.%20Development%20Plan_2026-07-11.md).

## 2. Переносимые уроки из ревью `agent` (что применить к human)

`agent` методологически родственен human (обе — физиологическая симуляция, solo + Claude Code + GSD). Его самые дорогие ошибки — это дешёвая профилактика для human:

| Урок из `agent` | Риск для human | Действие в этом плане |
|---|---|---|
| **0 git-коммитов** при ссылках на хэши как «доказательства» | У human уже закрыт (вики в git), но дисциплина коммитов должна сохраняться | Держать: коммит на каждую завершённую задачу; не ссылаться на несуществующие артефакты |
| **Красный тест, спрятанный за `xfail`**, подрывал доверие к «зелёному» гейту | У human 89 зелёных — не допускать «тихих» xfail | Любой отложенный тест — только явным issue с датой пересмотра, не забытым красным |
| **Дублирование физики ODE** (3+ копии) → реальный баг | Формулы движка в одном месте — сохранить это свойство | При добавлении v2-формул (EC50/Hill) не плодить копии; property-тест эквивалентности |
| **Нет `pip-audit`/`cargo-audit` в CI** | Транзитивные уязвимости незаметны | Phase 15: разовый `pip-audit` + шаг в CI |
| **Непоследовательный пиннинг** версий scientific-стека | У human все зависимости через `>=` без верхней границы | Phase 15: верхние границы или `uv.lock` |
| **Заявления сильнее реализации** («safety-gated», «audit-compliant») | У human — `biologicalAge` как «биологический возраст» вместо «индекса» | Phase 14: явная пометка ориентировочности в UI |
| **Bus factor = 1**, навигация только под ИИ (`.planning/`) | Человек с нуля проект не поднимет | Phase 15: README + архитектурная схема для человека |

**Ключевой вывод:** оба ревью и сквозной план **единодушно отвергают** сценарии C (масштабирование в мульти-юзер/облако) и D (переписывание). Для human это подтверждается: архитектурных блокеров нет, стек актуален, 89 тестов зелёные. План — **A (стабилизация) → B (постепенное развитие)** без смены архитектуры.

## 3. GSD-фазы Milestone v2.1

Разработка будет вестись через GSD, поэтому в этом документе больше нет внутренних «Фаза 0/1/2».
Ниже используются только реальные номера из `.planning/ROADMAP.md`.

### Phase 14 — UX Stabilization 2 (Стабилизация UX и документации)
Закрыть разрыв «готовый backend ↔ недоступная функция»:
- **[ ] Save/Load в UI** — кнопки/меню поверх готового [exporter.py](../src/engine/exporter.py); ручной round-trip через UI как критерий готовности (BL-06). Разблокирует основной сценарий «прервать и продолжить долгий прогон».
- **[ ] Пометка `biologicalAge` как ориентировочного индекса** в [src/ui/human_panel.py](../src/ui/human_panel.py) + tooltip со ссылкой на [Known Limitations](Known%20Limitations.md) (BL-07).
- **[ ] Пункт меню «Справка»** со ссылкой на [User Guide](../06%20-%20Engine/User%20Guide.md) и дисклеймер ограничений из самого приложения.
- **[ ] Переносимый `venv`** + примечание в README «venv не переносится между машинами/профилями, создавайте локально» (BL-04).

### Phase 15 — Foundation (Общий фундамент)
- **[ ] Верхние границы версий** в `requirements.txt` (или `uv.lock`) — снять риск breaking changes при переустановке (BL-08).
- **[ ] Лёгкий CI** (`pytest` на push) — запретить коммит «красного»; шаблон общий с mortality/agent.
- **[ ] `pip-audit`** разово + шагом в CI (BL-09).
- **[ ] README для человека** + архитектурная схема (база — §5 собственного review): онбординг без Claude Code.
- **[ ] Единая юридическая линия** (одна консультация на линейку) — достаточность дисклеймера про рецептурные препараты (метформин, рапамицин). Для v2.1 это **не release blocker**, а внешний checkpoint: зафиксировать вопрос и не усиливать медицинские утверждения до консультации.

### Phase 16 — UI Performance Stabilization (Производительность интерфейса)
Сделать дашборд отзывчивым без изменения биологической модели:
- **[ ] Обновлять только видимые графики** в `QScrollArea`.
- **[ ] Проверить PyOpenGL/GPU-рендер** только через замер до/после.
- **[ ] Зафиксировать benchmark** в документации фазы: software baseline, visible-only, OpenGL on/off.

### После v2.1 — не включать в Phase 14–16
Экспорт графиков, калибровка `mortality_risk.py`, субсуточные тики, циркадные ритмы,
генетический профиль, нелинейная PD, A/B-сравнение сценариев, mortality → human evidence-level
и Hovorka-модуль из `agent` перенесены в GSD-фазы **Phase 17–21** плана
[Milestone v2.2. Development Plan_2026-07-11](Milestone%20v2.2.%20Development%20Plan_2026-07-11.md).

## 4. Производительность UI — шаги 1 и 2

Из анализа торможения дашборда (24 живых графика PyQtGraph). **Корневая причина** — рендеринг идёт на программном (CPU) бэкенде; тротлинг до 5 fps, обрезка до 300 точек и GIL-паузы в коде — это борьба со следствием.

> **Область этого блока — только шаги 1 и 2.** Шаги 3–7 того же анализа (расточительное `list(buf)[-300:]`; пересчёт автомасштаба на каждый `setData`; переполировка QSS кнопок каждый кадр в [src/ui/time_controls.py](../src/ui/time_controls.py); `QThread.msleep(1)` с 15-мс гранулярностью Windows; поверхностный `model_copy()` как гонка данных) — **планируется к этому моменту уже выполнить** как рутинные точечные правки.

### Шаг 1 — Обновлять только видимые графики
- **Проблема:** [src/ui/telemetry_dashboard.py](../src/ui/telemetry_dashboard.py) в `update()` вызывает `setData` для **всех 24** плотов, хотя они в `QScrollArea` и одновременно видно ~6–12. Половина работы каждый кадр — впустую.
- **Действие:** данные копить в буфер всегда, а `curve.setData()` вызывать только для плотов, пересекающихся с видимой областью `QScrollArea.viewport()`.
- **Почему первым:** самый дешёвый и надёжный выигрыш, не зависит от рендерера, минус ~50% рисования за кадр.
- **Критерий готовности:** прокрутка дашборда плавная; невидимые плоты не тратят CPU на перерисовку; тесты [src/tests/test_ui_integration.py](../src/tests/test_ui_integration.py) и [src/tests/test_benchmark.py](../src/tests/test_benchmark.py) зелёные.

### Шаг 2 — Установить PyOpenGL и включить GPU-рендер
- **Проблема:** в [main.py](../src/main.py) включение `useOpenGL` обёрнуто в `try: import OpenGL`, но пакет **не установлен** (нет в `requirements.txt` и в `venv`) → все 24 плота рисуются QPainter на CPU. Именно на это ссылаются комментарии-костыли в [worker.py](../src/ui/worker.py) и [src/ui/telemetry_dashboard.py](../src/ui/telemetry_dashboard.py).
- **Действие:** добавить `PyOpenGL` (+`PyOpenGL_accelerate`) в зависимости, установить, убедиться, что срабатывает ветка `pg.setConfigOption("useOpenGL", True)`.
- **Оговорка:** для множества мелких PlotWidget-ов OpenGL иногда даёт собственный оверхед (свой GL-контекст на виджет). **Обязательно замерить до/после**; если хуже — основной выигрыш уже даёт Шаг 1, который работает и на software-рендере.
- **Критерий готовности:** при x100/x1000 окно остаётся отзывчивым; кадровое время рендера дашборда снижается (замер до/после зафиксирован).

## 5. Приоритетный порядок (ближайшие 2–4 недели)

1. **Phase 14:** Save/Load в UI; пометка `biologicalAge` ориентировочным; «Справка» в UI; переносимый `venv`.
2. **Phase 15:** верхние границы версий; лёгкий CI; `pip-audit`; README для человека; юридический checkpoint.
3. **Phase 16:** видимые графики → PyOpenGL под замер → benchmark до/после.
5. **Закрыть v2.1 release checklist:** тесты зелёные, ручной Save/Load round-trip пройден, UI-бенчмарк до/после зафиксирован, документация и Neo4j синхронизированы.
6. **После v2.1:** перейти к [Milestone v2.2. Development Plan_2026-07-11](Milestone%20v2.2.%20Development%20Plan_2026-07-11.md).

## 6. Чего НЕ делать

- **Не масштабировать** в мульти-юзер/облако/микросервисы (Сценарий C) — нет подтверждённого спроса (один оператор).
- **Не переписывать** архитектуру (Сценарий D) — нет технических оснований.
- **Не форсировать Фазу 4** (интеграцию трёх продуктов) до стабилизации каждого.
- **Не включать v2-механику в v2.1**: любые изменения формул, биологических допущений и межпродуктовых контрактов идут в v2.2+.
- **Не тянуть Streamlit-веб / Telegram-бот** из старого v2-backlog — для локального single-user инструмента это инфраструктура без потребности.
- **Не оптимизировать UI хаотично**: сначала Шаг 1 (видимые графики), затем Шаг 2 (PyOpenGL) с замером — не наоборот.
